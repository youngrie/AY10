# 基线校准与测量结果

本文记录**固定时长**与**基于队列（LQF）**两个基线的校准过程与最终指标，
作为 RL 智能体的对照基准。数据可用 `scripts/calibrate_baselines.py` 与
`src/evaluate.py` 复现。

## 实验设置

| 项目 | 取值 |
| --- | --- |
| 路网 | `nets/single-intersection/`，4 进口 × 4 车道（右/直/直/左），4 个绿灯相位 |
| 决策间隔 `delta_time` | 5 秒 |
| 每回合 | 3600 仿真秒 |
| 交通场景 | S1（600 veh/h）/ S2（1200）/ S3（2000）/ S4（1200，3:1:1:1） |
| 随机种子 | `sumo_seed` = 0 / 1 / 2，共 3 个 |
| 重复 | 每个 (控制器, 场景) 3 次，报均值 ± 标准差 |

> 早期结果不可复现的原因：`evaluate.py` 未把种子传给 SUMO（`sumo_seed` 默认为
> `"random"`）。现已修复，同一种子重跑结果一致。

## 固定时长的校准

原实现是"每 6 次决策轮转一次相位"，对 4 个相位等于**每相位 30 秒、周期 120 秒**，
结果比随机策略还差（12.0s vs 8.3s）——因为左转相位只承担 20% 的车流却占了 25% 的绿灯。

`scripts/calibrate_baselines.py` 扫描了「周期 × 绿信比」组合：

| 方案 | 配时（秒） | S2 平均等待 |
| --- | --- | --- |
| 旧（等长） | 30/30/30/30 | 12.00 |
| 均分 | 15/15/15/15 | 3.57 |
| **按需求分配** | **24/6/24/6** | **3.11** |
| 均分 | 19/19/19/19 | 5.71 |
| 按需求分配 | 30/8/30/8 | 5.02 |
| 按需求分配 | 48/12/48/12 | 10.83 |
| 均分 | 10/10/10/10 | 1.73 |
| **按需求分配** | **16/4/16/4** | **1.69** |

两个结论：

1. **按车流比例分配绿信比**（直行 ≈ 80%、左转 ≈ 20%）优于均分；
2. **周期越长越差**（本路口各进口远未饱和，短周期显著减少等待）。

⚠️ 但周期不能无限缩短：试过 `10/5/10/5`（周期 30 秒），左转只有 5 秒绿灯，
在 **S3 重载**下左转排队爆炸，平均等待飙到 **839 秒**。

**最终采用**（写入 `src/config.py` 的 `fixed_time.durations`）：

```json
"durations": [15, 5, 15, 5]      // NS直行 15s / NS左转 5s / EW直行 15s / EW左转 5s
```

由于决策间隔为 5 秒，实际执行的是 **15/5/15/5 秒**，加上每相位 3 秒黄灯，
信号周期约 **52 秒**。

## 测量结果（3 种子，均值 ± 标准差）

| 场景 | 控制器 | 平均等待 (s) | 平均队列 | 最大队列 | 平均速度 (m/s) |
| --- | --- | --- | --- | --- | --- |
| S1 | `random` | 7.75 ± 0.14 | 3.63 ± 0.34 | 21 | 5.04 |
| S1 | `fixed_time` | 1.79 ± 0.05 | 1.85 ± 0.12 | 8 | 5.82 |
| S1 | `queue_based` | **0.64 ± 0.08** | **0.89 ± 0.10** | 5 | 6.48 |
| S2 | `random` | 8.29 ± 0.24 | 8.07 ± 0.15 | 33 | 4.89 |
| S2 | `fixed_time` | 1.68 ± 0.01 | 3.62 ± 0.11 | 15 | 5.84 |
| S2 | `queue_based` | **1.26 ± 0.10** | **2.40 ± 0.17** | 12 | 6.25 |
| S3 | `random` | 8.99 ± 0.79 | 15.71 ± 1.40 | 55 | 4.60 |
| S3 | `fixed_time` | 1.88 ± 0.05 | 6.74 ± 0.25 | 21 | 5.71 |
| S3 | `queue_based` | **1.76 ± 0.04** | **4.99 ± 0.21** | 15 | 6.02 |
| S4 | `random` | 9.14 ± 0.18 | 9.81 ± 0.26 | 41 | 4.57 |
| S4 | `fixed_time` | 1.97 ± 0.08 | 4.16 ± 0.25 | 16 | 5.68 |
| S4 | `queue_based` | **1.50 ± 0.30** | **2.40 ± 0.18** | 11 | 6.23 |

## 结论

1. **`random` 是最差的下界**（7.75–9.14s），说明环境与指标工作正常，
   且"随便切灯"确实很糟。
2. **校准后的固定时长是一个体面的基线**（1.68–1.97s），不再出现
   "比随机还差"的荒谬结果。它的等待时间随需求上升而变差（S1 1.79 → S3 1.88），
   但幅度小，因为短周期本身就很能压低等待。
3. **LQF 始终优于固定时长**，但优势随负荷变化：
   - 轻载 S1：0.64 vs 1.79（**2.8 倍**）
   - 中载 S2：1.26 vs 1.68（1.3 倍）
   - 重载 S3：1.76 vs 1.88（**仅 1.07 倍**）
   - 不均衡 S4：1.50 vs 1.97（1.3 倍）
4. 也就是说，**负荷越高，固定时长与 LQF 的差距越小**。这符合直觉：
   接近饱和时，任何"轮流放行"的方案都会被容量瓶颈主导。
   RL 若想在重载场景体现价值，必须学会在**不均衡**（S4）和**方向差异**上做文章，
   而不是简单地"谁排队长放谁"。

> 对报告的意义：RL 的对照基准应是 **LQF**（而非固定时长）。
> 在 S3 想赢 LQF 只有 7% 的空间，因此更有说服力的做法是展示
> **S1/S2/S4 上的提升幅度**，以及 RL 学到的策略与 LQF 的差异。

## 复现

```bash
# 重新校准固定时长
python scripts/calibrate_baselines.py --scenarios S1 S2 S3 S4 --cycles 30 40 60

# 复测三个基线（3 种子）
python src/evaluate.py --scenarios S1 S2 S3 S4 \
    --controllers random fixed_time queue_based --seeds 0 1 2
```

结果写入 `results/eval_<场景>.csv`（合并写，不会冲掉历史行）。

> 原始逐步 CSV 默认会被删除（文件名带 `conn0/conn1/…` 会无限累积）。
> 需要画时间序列/学习曲线时加 `--keep-raw`。

## 注意

- 改车道数或相位数量后，**必须重新校准并重跑**（`observation_space` 也会变）。
- 基线参数已固化在 `src/config.py`，命令行不再覆盖，保证对照可复现。
- `max_queue` 取 3 次运行中的最大值；`mean_speed` 为系统级平均车速。
